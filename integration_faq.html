Common Questions

These answers are written to avoid overclaiming. If a point depends on your exact usage, the answer tells developers to verify it through documentation, testing, or a direct discussion.

Do you have full API documentation?

Start with the official documentation: https://docs.linkshieldai.com/.

Developers should review the endpoint details, expected request format, response fields, and any available examples before integrating. If a required example or error case is missing, ask for clarification before using it in production.

What data is stored or logged when URLs are submitted?

Review the official privacy policy before production use: https://linkshieldai.com/privacy-policy.html.

For a first technical test, developers can use non-sensitive sample URLs or historical test data instead of sending live user traffic.

Is the API intended for commercial Discord bots?

If the bot is commercial, the developer should review the official Terms of Service before relying on the API in production: https://linkshieldai.com/terms-of-service.html.

A controlled test can still be run first to evaluate technical value before discussing production usage.

What are the pricing options beyond the free developer tier?

The free developer tier is useful for evaluation. For production usage, pricing should be discussed based on request volume, peak traffic, and the bot's use case.

Ask the developer for approximate monthly URL scan volume and whether they want to scan every link or only suspicious links.

If payment or plan terms are involved, developers should also review the refund and cancellation policy: https://linkshieldai.com/refund-policy.html.

If you don't want to discuss pricing, refer to the official pricing page on the developer portal: Here.
Do you provide uptime or reliability guarantees?

Reliability requirements should be discussed before production integration, especially for high-traffic moderation bots.

For evaluation, run LinkShieldAI in logging mode first. That lets the bot compare results without depending on the API for immediate enforcement.

How should false positives be handled?

Use LinkShieldAI as a signal first, not as the only reason to punish a user.

  • Log uncertain results for moderator review.
  • Let your existing allowlist override automatic action.
  • Compare LinkShieldAI results with your current scanner.
  • Only automate stronger action after testing real results.
Can I test without Discord or bot permissions?

Yes. A developer can test with direct API requests from a local script, dev environment, private test bot, or backend service.

No Discord bot token, server invite, or bot permission is needed just to evaluate URL analysis results.

Does LinkShieldAI replace my current protection?

It does not have to. The safest starting point is using LinkShieldAI as an additional detection layer or secondary signal.

That means your current system stays in place while LinkShieldAI results are logged, compared, and evaluated.

What if my bot already uses VirusTotal, Google Safe Browsing, or another provider?

Keep the existing provider and test LinkShieldAI beside it.

The practical question is whether it adds useful signal for phishing, scams, crypto-scam patterns, suspicious redirects, or Discord-focused abuse cases your current stack may miss.

What is the safest first test?

Start in logging mode. The bot sends URLs to LinkShieldAI, records the response privately, and takes no automatic moderation action at first.

After reviewing enough results, decide whether to use it for mod alerts, message deletion, warnings, or higher-confidence enforcement.

Which SDKs are available?

Official package links provided by LinkShieldAI:

  • Python SDK
  • JavaScript SDK
  • PHP SDK
  • Rust SDK

Other languages can evaluate the API through direct HTTP requests if supported by the documentation.

Can detection be guaranteed?

No security API should promise perfect detection. Threats change, domains rotate, and new campaigns appear constantly.

The correct way to position LinkShieldAI is as another layer of analysis that can improve decision-making when combined with existing moderation rules and review workflows.

What should a production discussion include?

Before production use, discuss expected request volume, peak traffic, acceptable latency, reliability expectations, pricing, data handling, and how moderation decisions will be made.

This keeps the conversation professional and prevents surprises later.

What sample should I test against?

Use a mix of known safe URLs, known malicious or suspicious samples from your own moderation history, shortened URLs, newly seen domains, and URLs your current system was unsure about.

The goal is not a perfect lab result. The goal is to learn whether LinkShieldAI adds practical value to your bot's existing workflow.

Can I use direct API requests instead of an SDK?

Yes, direct API requests are a good option when a developer wants to keep dependencies low or uses a language without a published SDK link.

The SDKs are useful for convenience, but the integration decision should depend on the bot's architecture and the examples in the official documentation.

Where should LinkShieldAI sit in my moderation flow?

A practical first placement is after URL extraction and before enforcement.

The bot sees a URL, sends it for analysis, logs the result, and only later decides whether the result should affect warnings, deletions, mod alerts, or automatic moderation.

Should I scan every link or only suspicious links?

Both models can make sense. Scanning every link gives broader coverage, while scanning suspicious links can reduce request volume.

For high-traffic bots, start with suspicious patterns such as shortened URLs, new domains, unknown domains, giveaway language, crypto-related messages, or links your current system cannot classify confidently.

What happens if the API is unavailable?

Your bot should define a fallback behavior before production use.

Common options include logging the failure, falling back to your existing scanner, sending the URL to moderator review, or allowing the current system to make the decision without LinkShieldAI for that request.

How should API keys be handled?

Treat API keys as secrets. Keep them out of public code, client-side code, screenshots, and shared logs.

For bot projects, store the key in environment variables or a private secret manager and rotate it if it is exposed.

Can I test on historical moderation logs?

Yes, if your privacy rules and server policies allow it. Historical URLs are useful because you can compare LinkShieldAI's result against what Guardian or another bot already decided.

When in doubt, use anonymized or non-sensitive samples for the first evaluation.

How long should a controlled test run?

Long enough to see a meaningful mix of safe, suspicious, and malicious-looking URLs. For a small bot, that may mean a focused sample set. For a larger bot, a few days of logging mode may be more useful.

The right test length depends on traffic volume and how often the bot sees links.

What information should I send for a production quote?

Share approximate monthly URL checks, peak request bursts, whether you scan every URL or only suspicious ones, and whether the bot needs special reliability expectations.

That gives enough context to discuss a realistic production plan without guessing.
